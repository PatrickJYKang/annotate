# Annotate 0.2 – Scope and Phasing

Date: 2026-07-07
Status: Planning
Companion: [project-v2-schema-and-migration.md](project-v2-schema-and-migration.md)
Implementation: [implementation-plan.md](implementation-plan.md)

## Purpose

This document lists the set of changes that constitute version 0.2. It is the
planning umbrella for the redesign discussed after the 0.1.0-pre.2 release;
the companion document sketches the `project.v2` on-disk schema and the plan
for migrating the application code to it.

0.2 is a breaking release with **no backwards compatibility**: it does not
read, write, or convert `project.v1` folders — they are refused with a clear
message, and old projects stay on 0.1 via the pinned release tag.
"Migration" in the companion document means migrating the application code
to the v2 model, not migrating data.

---

## The change set

### 1. Clips become the unit of analysis (data model)

- Marks and stills are removed as first-class entities. Both collapse into
  the clip:
  - a former **mark** is a clip-local **frame pin** (the moment you choose to
    annotate);
  - a former **still** is an **annotation document pinned to a frame** of a
    clip.
- Tags move from marks to **clips**. The tag folder tree, exports, and the
  presentation asset browser group and filter by clip tags.
- The annotate workflow becomes: open a clip → scrub to a moment → press
  **Annotate** → the annotation editor opens for that frame → saved
  annotations are stored under the clip.
- **Pin annotations are independent of the clip's own annotations.** A pin's
  annotation documents (still-style drawings for that frame) have nothing to
  do with the clip's keyframed/animated annotations; they are separate
  layers with separate storage.
- **Presentations: the default slide unit is the clip.** Pins act as
  automatic pause points during clip playback (play → pause at pin → show
  the pin's annotations → resume); each slide can deselect pins it does not
  want to pause on. Using a pin directly as a slide remains possible, but it
  is the secondary path, not the default.

### 2. Frames replace milliseconds

- All stored and app-level time values become **integer frame indices**;
  milliseconds survive only at the `<video>.currentTime` boundary.
- Well-defined because imports are already normalized to project FPS; frame
  indices are relative to the owning video's stored fps.
- Details and conversion rules in the companion schema document.

### 3. Tagging window (replaces pause → menu)

- A persistent tagging panel with buttons, in the style of a Sportscode code
  window, defined by a per-project **`tagging-board.json`**.
- **`tagging-schema.yaml` is replaced, not extended.** The v1 schema modeled
  a dropdown tree; the v2 artifact models a button board, and JSON fits the
  structure better than YAML. The board defines the tag vocabulary directly
  (buttons carry tag identity; toggles carry facets); the tag folder tree
  view derives its grouping from the board.
- Pressing a tag button creates a tagged clip around the current playhead
  (lead/lag), and/or press-to-start / press-to-stop range capture — see open
  decisions. Buttons carry per-button `hotkey`, `leadFrames`, `lagFrames`,
  and `mode`.
- Replaces `TaggingMenu` and the pause → context-menu flow entirely.

### 4. Hierarchy: Analysis ∥ Presentations (UI and disk)

- The project dashboard presents two parallel wings: **Analysis**
  (videos → clips) and **Presentations**. Neither is downstream of the other
  in navigation; analysis stays video-scoped inside its wing.
- On disk, analysis data moves under `analysis/`, so the layout states the
  hierarchy: `media/` | `analysis/` | `presentations/`. Each clip is a
  **self-contained folder** (`analysis/clips/<clipId>/` holding `clip.json`
  and that clip's pin-annotation documents) — see the companion doc for the
  under-clip vs parallel-tree trade-off.
- Exports remain renders (PNGs, MP4s, reports) written under `exports/`;
  source media is referenced, never copied into export folders.

### 5. Panelization

- Every screen is composed of resizable panels (Photoshop-docked, not
  windowed). Splitter-resizable sizes persisted per route; interactive
  rearranging of panel positions is explicitly out of scope for 0.2 (design
  the panel tree so it could come later).
- Implementation direction: `react-resizable-panels` as the one new
  dependency, panel shell applied to the clip editor first (viewer /
  timeline / tagging window / inspector / clip tree), then the remaining
  screens.

### 6. Deletions

The redesign removes:

- `/stills` page, still capture, thumbnail management
- mark machinery (`marks[]`, mark pinning, `sourceMarkId` integrity repairs —
  replaced by v2 integrity checks)
- `TaggingMenu` and the `/dropdown-test` sandbox
- `/player-legacy`

### 7. Internationalization — always the last phase

- Chinese (zh-CN) first; other languages after.
- The i18n *mechanism* (a light client-side `t()` layer with a locale toggle;
  no URL-locale routing for a local tool) can land early, but **string
  extraction happens only after screens stop churning** — extracting from
  screens that phases 1–5 rewrite or delete would be wasted work twice over.
- Per direction: language work always sorts to the end. If 0.2 runs long,
  i18n slips to 0.3 rather than delaying the structural work.

### 8. Quick annotate — isolated

- `/quick-annotate` stays as-is: own route, OPFS-backed, no shared state.
  It is not deepened into the new model. If any 0.2 refactor breaks it, it is
  quarantined or removed rather than accommodated; long-term it is a
  candidate for extraction into a separate repo/deployment.

## Explicitly deferred (not 0.2)

- **Dependency trim.** Install time is dominated by the sidecar's CV stack
  (PyTorch, TensorFlow, OpenCV, Ultralytics) plus webapp TensorFlow.js.
  Acknowledged as too heavy; deliberately parked to keep building. Revisit as
  a 0.3 candidate (ideas: optional extras split for the sidecar, lazy model
  installs, dropping browser-side ML occlusion if the sidecar path is
  sufficient). The 0.2 deletions may drop a few incidental packages; take
  those opportunistically, don't chase them.
- Windowed/floating UI (rejected, not just deferred).
- Drag-to-rearrange panel docking (design for it, don't build it).
- Any `project.v1` support at all — read, write, or data migration. Old
  projects stay on 0.1 (pinned release tag).

## Phasing

| Phase | Work | Notes |
|---|---|---|
| 0 | `project.v2` schema + frames-not-ms + v1 refusal | Foundation; see companion doc §4 for the code-migration order |
| 1 | Clips-as-unit: tags on clips, frame pins, clip-scoped annotations, delete marks/stills, rework exports | Largest phase; biggest deletion |
| 2 | Tagging window + tag-to-clip capture workflow | Consumes phase 1's model |
| 3 | Hierarchy/nav: Analysis ∥ Presentations, `analysis/` folder move | Mostly navigation + dashboard |
| 4 | Panelization (clip editor first) | Shell over stabilized screens |
| 5 | i18n mechanism + zh-CN extraction | Always last; may slip to 0.3 |

Each phase lands green (unit + e2e; fixtures re-authored as native v2 in
phase 0–1, regenerated again for the phase 3 layout).

## Open decisions (defaults proposed, not yet confirmed)

1. **Tag button behavior** — proposed: both modes, per-button in the board
   (`mode: instant` with lead/lag vs `mode: range` press-to-start/stop);
   default `instant`.
2. **Export packaging** — current reading: exports are renders and never copy
   source media; confirm nothing more is meant (e.g. a share-project bundle
   is new scope, not 0.2).
3. **i18n breadth** — zh-CN only for 0.2's final phase, zh-TW later? Should
   the default tagging board template ship bilingual?
4. **Risky-deletion confirmation** — `/player-legacy` and `/dropdown-test`
   removal assumed OK per §6.
5. **Annotation storage location** — sketched as **under each clip folder**
   (self-contained clip unit: one folder to delete/copy/inspect, orphan
   annotation documents structurally impossible). The alternative — a
   parallel `analysis/annotations/<clipId>/` tree keeping clips as single
   files — is noted in the companion doc. Veto before phase 0 if the
   parallel layout is preferred.

## Risks

- **No-data-migration stance**: anyone with a meaningful 0.1 project keeps
  it on 0.1; nothing carries forward. Accepted deliberately — pre-release
  install base, and a correct migrator would cost more than the data it
  would save.
- **The long code-swap window**: phases 0–1 rework the model under the whole
  app. Mitigation is the ordered steps in the companion doc §4.3 — each step
  lands green, and v1 types are deleted last so the compiler acts as the
  completeness check.
- **ClipEditor growth**: the clip editor is already the largest component
  (~4.8k lines) and phases 1–4 all touch it. Budget for splitting it along
  panel boundaries during phase 4 rather than letting it absorb everything.
- **e2e fixture churn**: both fixture projects embed marks/stills; they are
  re-authored as native v2 in phases 0–1, which temporarily reduces browser
  coverage until the specs are rewritten.
