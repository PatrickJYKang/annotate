## Open-source distribution approach

Use the source-accompanying-download approach in GPLv3/AGPLv3 section 6(d), rather than promising a three-year written source offer. Every published installer must have matching Annotate source, relevant third-party corresponding source, licence texts, dependency versions, modifications and build/install instructions available at no additional charge from the release page. Preserve those files for as long as the binary is offered. A link to a changing main branch is not a substitute for matching source.

AGPLv3 section 13 permits combining AGPLv3 and GPLv3 parts while retaining their respective terms. We therefore do not require a commercial Ultralytics licence merely because this is a desktop product, and we are not relicensing third-party code or automatically changing Annotate's own licence. The combined work's applicable source and network-interaction obligations still apply. The desktop Help menu exposes licence files and matching source; the browser header links to its build's source commit. A source archive without Git metadata links to the repository rather than inventing a commit. A local dirty build is not represented as the exact public source of a distributable release.

The source release needs the actual integrated application and build scripts, not just Ultralytics by itself. `desktop/compliance/sources.lock.json` pins the upstream source distributions for `ultralytics` and `ultralytics-thop`; staging checks them against the Python dependency lock, downloads without executing them, verifies SHA-256, and includes them under `runtime/licenses/sources/`. The YOLO weight file remains in the runtime with its existing pinned checksum and AGPL attribution. This addresses source collection for those Python packages, not all native dependencies. PnLCalib's former permission questions are resolved separately below.

## Notices and evidence

The notice collector includes the actual server runtime and installed non-development browser build inputs, including libraries compiled into client bundles. It also copies nested notices in Next's vendored code, Python wheel notices outside `.dist-info` such as OpenCV's, the font licence, and the project's full GPL text. Python metadata uses explicit licence fields or licence classifiers; absence of evidence is not treated as a permissive licence. Exact-version supplements restore the upstream Next 15.5.28 MIT notice to `@next/env` and `@next/swc-*`; the env supplement also preserves the BSD notices of its bundled dotenv 16.3.1 and dotenv-expand 10.0.0. The texts and provenance checksums are in `desktop/compliance/notices/`. Unknown future versions do not inherit these supplements silently. Legacy `client-only@0.0.1` remains explicitly flagged if encountered in old staging; new builds use the independently authored marker described above.

`npm run prepare:compliance -- darwin-arm64` (or `win32-x64`) reads an already staged runtime (or the optional third CLI argument naming an isolated runtime) and creates a separate, uniquely named evidence directory and archive under `desktop/artifacts/compliance/`. It contains the current review, notice inventory, checksum-verified upstream archives, staged media-tool sources/recipes, and committed application source. Dirty-tree runs are explicitly marked and include a patch of tracked edits; untracked files are listed but not automatically copied, to avoid exposing unrelated local files. The staged runtime can predate the working tree. These are review artifacts, not publishable corresponding-source bundles. The archive deliberately states that compliance is incomplete while the following gates remain open. It does not modify existing installers, staged runtimes or published source archives.

The selected path is the controlled replacement, not another maintainer email. Validate it against the app's real import, playback, tracking and export workflows on Windows before adopting it.
